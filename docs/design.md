# Javdex Runtime 设计方案

Javdex Runtime 统一交付 Javdex 使用的原生运行库和辅助工具。构建与发布集中到本仓库，下载、准备计划、安装和任务执行仍由 Javdex 管理。首期只迁出 Windows x64 的 Whisper Vulkan 运行库，保留以后增加其他原生扩展的空间，不一次性搬迁所有依赖。

本方案于 2026 年 10 月 18 日建立。仓库创建与设计文档是本次交付；构建实现、运行库发布和 Javdex 接入尚未开始。

## 职责分工

| 内容 | Javdex Runtime | Javdex |
| --- | --- | --- |
| 原生程序 | 固定源码、构建、打包及发行 | 固定引用一个已发布版本 |
| 发行材料 | 包大小、摘要、文件清单、来源和许可 | 在执行任何下载内容前验证消费锁定 |
| 准备与安装 | 不接触用户目录或设备设置 | 计划预览、断点续传、校验、暂存与原子安装 |
| 推理与设备 | 提供明确的命令行接口和已验证能力 | GPU 枚举、选择、显存预算、任务租约及 CPU 回退 |
| 模型权重 | 首期不托管、不重新分发 | 保持现有模型身份、来源和精度管理 |
| 应用更新 | 不发布桌面应用或服务端升级包 | 保持原有发布流程及信任根 |

运行库发行模块向消费方只暴露固定下载地址、摘要、包格式和命令行接口；工具链与构建细节留在实现内部。不新增运行库专用 SDK 或第二套客户端组件管理器。

未来的文本引擎、语音引擎、媒体工具、设备探测工具可以加入同一仓库。业务插件、任意远程脚本和模型市场不因仓库名称通用而自动纳入；新增类别先明确调用接口、权限和安装行为。

## 首期交付

首个运行库为 `whisper`，变体为 `win32-x64-vulkan`。沿用 Javdex 0.9.0 当前固定的 whisper.cpp 提交 `927cfce34f31707e17f2bff35c349632fb9e2c3a`，对应 b5130；迁出时不顺带升级引擎、模型或计算策略。

复用当前 Whisper Vulkan 构建配方的行为：启用 Vulkan，关闭 CUDA、CURL、OpenMP、本机 CPU 指令探测及 AVX 扩展，使用静态 MSVC 运行库。保留完整解码固定 Zstandard 归档后再交给 Windows tar 的修复。迁移配方时先核对代码许可，不直接给复制代码改换许可证。

交付只包含 `whisper-cli.exe`、必要的 `vulkan-1.dll`、许可证、来源和运行库清单。不分发编译器、完整 Vulkan SDK、显卡驱动、测试音视频或模型权重。

现有第三方预编译发行可作为后续来源候选。采用第三方构建前必须重新核对来源、接口、依赖与模型兼容性；不能只改 URL 却保留自建包的摘要或身份。

## 版本与发行身份

运行库独立发布，不使用 Javdex 的 `0.9.0` 作为仓库统一版本。首期命名示例为：

- Release 标签：`whisper-b5130-r1`。
- 运行库附件：`whisper-b5130-r1-win32-x64-vulkan.zip`。
- 发行清单：`release.json`，列出该次发行的实际目标、附件大小和 SHA-256。
- 其余材料：`SHA256SUMS.txt` 以及该构建实际需要的来源和许可材料。

`r1` 是构建修订。更换编译参数、依赖、源码补丁或包内容，均产生新修订；同一上游版本并不代表相同二进制。新增平台附件也应进入新修订，不能在固定旧发行中追加或替换。

其他运行库使用自己的标签前缀，例如文本引擎不必随语音引擎一起发版。Javdex 不使用本仓库的 `latest` 判断某种运行库的新版本，因为不同引擎没有共同的版本顺序。

发行身份至少包括运行库标识、上游完整提交、构建修订、系统、架构、后端和命令行接口版本。编译器版本、依赖锁、构建配方摘要、仓库提交和 CI run 另记为来源信息；在没有字节对照前，不把“来源固定”称为“二进制完全可重现”。

## 下载包与清单

Windows 首期采用单一用途的平铺 ZIP，不把多个后端或模型混成一个大包：

```text
whisper-cli.exe
vulkan-1.dll
LICENSE-whisper.txt
LICENSE-vulkan-loader.txt
LICENSE-vulkan-headers-...
SOURCE.json
runtime.json
```

`runtime.json` 描述归档内文件，`release.json` 描述整个发行附件。两者避免自引用摘要：文件清单不计算自身摘要，外层归档大小和摘要只由打包结束后生成的发行清单记录。

| 清单内容 | 约束 |
| --- | --- |
| `formatVersion` | 首期为 1；未知格式拒绝，不猜测兼容 |
| 运行库身份 | 与消费锁定的引擎、系统、架构和后端严格一致 |
| 命令行接口 | 单独标识支持的接口版本及经过测试的能力，不用上游版本号代替兼容性检查 |
| 入口及文件 | 固定相对入口、逐文件大小与 SHA-256，禁止隐含或额外可执行文件 |
| 宿主条件 | 记录实际需要的系统、CPU、驱动条件；不从 Vulkan 头文件版本推断最低驱动 |
| 来源与许可 | 完整源码提交、依赖锁、补丁与配方来源，以及所需第三方许可材料 |

所有大小与摘要由 CI 对实际输出计算，不在设计或模板中填入虚构值。清单不能指定安装后脚本、任意命令、系统安装目录或注册表修改。

后续 POSIX 变体可以采用保留布局和执行位的归档；只有存在实际目标时，才实现对应格式和依赖解析。

## 消费锁定与安全

Javdex 源码固定记录运行库的 Release 标签、附件 URL、实际压缩大小和 SHA-256。远程 `release.json` 可用于维护者生成更新提案，但不能自行授权客户端更换程序。Javdex 也不把同一下载地址附带的校验和当成独立信任来源。

下载和安装按以下顺序执行：

1. 用户请求准备对应能力，Javdex 展示网络下载和本地安装计划。
2. 复用现有有界下载、取消、断点续传及缓存机制。
3. 先核对整个归档的固定大小和 SHA-256，再处理内部清单和文件。
4. 在受控暂存目录提取，限制文件数和解压总量，拒绝路径穿越、链接、重名、大小写冲突和清单外文件。
5. 核对目标、入口、逐文件摘要及接口，再沿用任务租约和原子晋升流程；失败保留可用旧安装，不先删后装。

当前 Windows 解压器只筛选指定 EXE、DLL 和许可文件，不能把新包协议接入简化成“换一个 URL”。实施时应显式校验 `runtime.json` 和来源材料，同时保留已有下载与安装模块，不另写管理器。

首期沿用应用内固定摘要的消费信任方式，不引入自动信任的远程目录，不复用或轮换 Javdex 的服务端 Ed25519 密钥或应用签名密钥。GitHub 构建证明可补充来源证据，但不代替客户端固定摘要和兼容性检查。

## CI 与发布流程

`check.yml` 在 PR 上检查来源锁、清单格式、命名、包布局和相关脚本测试，不授予发布权限。`build.yml` 在相应原生 runner 上构建与检查。`release.yml` 在维护者明确选择固定源码和目标后发布，不因普通推送自动公开运行库。

构建检查应覆盖原生程序架构和 DLL 闭包、隔离工作目录与受控 PATH 下的启动、命令行参数、输出格式、取消，以及 Kotoba/VAD 所需的兼容行为。构建依赖只能留在构建目录；客户端无需安装完整开发 SDK。

普通托管 Windows runner 不等于真实 Vulkan 显卡。加载或 CPU 路径通过只能证明对应行为；GPU 初始化、选卡和实际语音推理需要真实支持设备的证据，不能把无设备跳过记为 GPU 通过。发布清单如实记录检查范围，Javdex 接入默认能力前仍需满足自己的兼容门禁。

发布采用单一固定身份的串行流程：

1. 核对目标清单、源码提交、标签与附件均没有已公开的同身份版本。
2. 构建、检查并生成归档、实际清单、摘要和来源材料。
3. 创建 Draft Release，上传同一构建的全部材料，核对附件集合。
4. 全部通过后一次公开，启用并确认 GitHub Release immutability；公开后不追加或替换附件。

GitHub 的不可变发行会锁定关联标签和附件，且建议先准备 Draft 再公开。该能力属于实施阶段要配置的仓库设置，当前未启用或验证。参考 [Immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)。

构建任务默认只读；只有最终发布任务取得必要写权限。第三方 Actions 固定到提交，不在持有发布权限的任务中执行未经审核的 PR 代码。需要构建来源证明时采用 GitHub 提供的机制，见 [Using artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations)。不承诺此类证明可以替代恶意代码审查或实际运行检查。

## Javdex 接入

只有本仓库首个固定运行库发行就绪后，才在 Javdex 后续版本接入：

1. 在 `gpuManifest.ts` 填入实际附件 URL、大小与摘要，去掉对应的 `bundledVersion`，改为下载交付。
2. 调整有界归档验证以接受本包协议，保持准备计划、进度、缓存身份、取消、任务租约及原子安装规则。
3. 确认已准备、尚未准备、取消续传、校验失败、缺 DLL、显存不足与 CPU 回退均有回归；有效旧运行库不会仅因换分发方式而被无条件删除。
4. 在验证下载路径可用后，移除 Windows 打包期间的 Whisper Vulkan 编译与随包复制；保留其他平台和其他引擎原有行为。
5. 通过 Javdex 正常 PR、构建和后续版本发布交付，不覆盖已经公开的 0.9.0。

迁出分发方式不修改用户翻译设置、模型权重、自动模式 CUDA 优先级或 GPU 回退规则。现有 Vulkan 设备枚举依赖文本引擎，首期保留；轻量独立探测器可作为后续明确任务加入同一仓库。

## 扩展规则与实施顺序

新增运行库时，只需增加真实来源锁、目标配方、入口接口和检查；共用包协议、发布材料与消费锁定规则。已有可靠上游发行时，可以继续让 Javdex 固定引用上游，不为了“统一”而重新托管或重建全部第三方二进制。

先完成 Windows Whisper Vulkan 的单一闭环，再考虑 macOS AI 工具、其他文本引擎变体或设备探测工具。跨平台迁移、签名、公证和重新分发权利分别评估，不由 Windows 首期自动授权。

实施分三步：先完成独立构建与包协议，再发布首个固定运行库，最后通过独立的 Javdex 变更接入并验证主包体积变化。当前停止在方案阶段，不创建工作流、不下载产物、不发布运行库，也不对 Javdex 主仓库产生提交。
